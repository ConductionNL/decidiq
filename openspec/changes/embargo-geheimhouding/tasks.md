### Task 4: Bekrachtiging workflow — agenda placement, besluit link, fail-visible overdue
- **spec_ref**: `openspec/changes/embargo-geheimhouding/specs/embargo-geheimhouding/spec.md#requirement-req-emb-003-bekrachtiging-workflow-with-fail-visible-overdue-flag`
- **files**: `lib/Service/GeheimhoudingService.php`, `lib/Controller/GeheimhoudingController.php`
- **acceptance_criteria**:
  - GIVEN a ground with `requiresBekrachtiging: true` WHEN the geheimhouding is imposed THEN an AgendaItem referencing it is created on the confirming body's next scheduled meeting and `bekrachtigingDeadline` defaults to that meeting's date (manually overridable)
  - GIVEN a linked bekrachtigingsbesluit Decision WHEN bekrachtig is called THEN state becomes `bekrachtigd` with besluit UUID + timestamp; WHEN the ground needs no bekrachtiging THEN 409
  - GIVEN a passed deadline without besluit WHEN the register is viewed THEN the geheimhouding is flagged overdue, its state remains `opgelegd`, and the target remains confidential (never auto-lift)
- [x] Implement
- [x] Test
- Built (21 Nov): `ConfidentialityRatifier`. On imposing (`POST /api/confidentiality/restrictions/impose`, new optional `ratifyingBody` and `ratificationDeadline`), when the ground requires ratification (or cannot be read), a closed agenda item "Bekrachtigen geheimhouding <subject>" (`itemType: decision`, `confidentiality: confidential`, `public: false`) is created last on the ratifying body's next draft or scheduled meeting from today, linked as `ratificationAgendaItem`, and `ratificationDeadline` is that meeting's date unless a deadline was given. The ratifying body defaults to the imposing body. The answer says `ratification`: `not-needed`, `placed`, `no-meeting` or `not-placed`; a failed placement is reported, not raised. `POST /api/confidentiality/restrictions/{id}/ratify` with `ratificationDecision` moves an `imposed` restriction to `ratified` with the decision and the time: 404 unreadable, 403 without the authority of the imposing body or of the body whose meeting holds the item, 400 no decision, 409 not imposed or its ground needs no ratification, 422 unknown decision. Nothing reads the deadline to change the state: an overdue restriction stays `imposed` and its target closed; the overdue state shows through the declared ratification-due notification and the register's deadline column (the lapse of confidentiality-term-and-lapse REQ-EMB-021 is the one exception). Tests: `ConfidentialityRatifierTest` (7), `ConfidentialityRestrictionControllerTest::testRatify` and the placement in `testImposedIsCreated`.

### Task 5: Opheffing workflow — besluit + conditions, eligibility restored, never auto-public
- **spec_ref**: `openspec/changes/embargo-geheimhouding/specs/embargo-geheimhouding/spec.md#requirement-req-emb-004-opheffing-workflow-routing-into-the-normal-publication-machinery`
- **files**: `lib/Service/GeheimhoudingService.php`, `lib/Controller/GeheimhoudingController.php`
- **acceptance_criteria**:
  - GIVEN an opheffingsbesluit by the imposing/confirming body WHEN opheffen is called THEN state becomes `opgeheven` storing besluit UUID, date, and optional conditions, and the target classifier returns to its non-public default (`internal`), audit-trailed
  - GIVEN an opgeheven geheimhouding WHEN no griffie member has run the publish flow THEN the target appears on no public surface; WHEN the normal publish flow runs THEN it accepts the target
- [x] Implement
- [x] Test
- Built (21 Nov): `POST /api/confidentiality/restrictions/{id}/lift` (`ConfidentialityRestrictionController::lift`, `ConfidentialityLifter`, in `openapi.json`) with `dissolutionDecision` and optional `liftingConditions`. The restriction is read with the caller's rights (404), then the caller needs the same authority as for imposing, on the restriction's `imposedByBody` (403). Refused: no decision (400), an unknown decision (422), a restriction no longer in force, or one still `imposed` whose ground needs ratification or cannot be read (409, the same rule `LiftAfterRatificationGuard` enforces on the save). The restriction moves to `dissolved` with the decision, today's `liftingDate` and the conditions, every other field kept, written as the system (the register lets only administrators update a restriction). The target's classifier goes from `confidential` back to `internal`, never `public`, unless another active restriction still closes it; a failed save leaves it confidential and answers `not-updated`. `dissolved` is not an active state, so the normal publish flow accepts the target again and nothing is published on its own. Tests: `ConfidentialityLifterTest` (9), `ConfidentialityRestrictionControllerTest::testLift`. The lifting dialog is task 8.
